# Заключение и отчёт по доработке инвайтинга

Добрый день.

Ниже — итог работы по вашему ТЗ: разбор текущей логики, причины ошибок, что изменено в коде, как теперь должна вести себя очередь, и оценка стоимости.

---

## 1. Суть проблемы

У вас мультиаккаунтный инвайтер на FastAPI + Telethon + SQLite. На практике картина такая:

- старый аккаунт стабильно добавляет людей в целевой чат;
- новые аккаунты авторизованы, ходят через прокси, проходят preflight, но результат заметно хуже;
- часть запросов Telegram отвергает через `missing_invitees`;
- часть запросов Telegram принимает без исключения, но после пяти проверок пользователя в чате всё равно нет («тихая потеря»);
- у старого аккаунта накоплено порядка 16 000 `access_hash`, у новых — десятки–сотня;
- после неподтверждённого приглашения создавалось ощущение, что аккаунт «съел» суточный лимит / ушёл в длинную паузу зря;
- при параллельной работе периодически всплывал `database is locked`.

Задача была не «накрутить обход лимитов», а сделать учёт и очередь честными относительно того, что реально ответил Telegram.

---

## 2. Почему старые аккаунты лучше новых

Главная техническая причина — **per-account `access_hash`**.

Хэш пользователя валиден только для того Telegram-аккаунта, который его получил. Чужой хэш использовать нельзя: будет `PEER_ID_INVALID` или некорректный peer.

Как резолвится цель сейчас (и как должно):

1. есть свой hash в таблице `hashes` → `InputPeerUser(user_id, own_hash)`;
2. иначе есть `@username` → получаем entity через username и сохраняем hash уже для этого аккаунта;
3. иначе — цель для данного аккаунта недоступна (`no_hash`).

Отсюда и разница пула: старый аккаунт «видел» аудиторию много раз и накопил хэши; новый без своего hash и без username объективно слеп к части базы.

Вторая причина — сам Telegram. Даже при корректном peer API может:

- вернуть человека в `missing_invitees`, либо
- принять Invite RPC без ошибки и без `missing_invitees`, но не добавить участника.

Это нельзя лечить повторной безусловной отправкой Invite: так вы только ускоряете FloodWait / PEER_FLOOD. Правильная модель — считать успехом только подтверждённое присутствие в чате.

Практическая рекомендация: парсить доноров **теми же аккаунтами**, которыми потом инвайтите, чтобы у каждого копился свой hash.

## 3. Как должна работать очередь (и как сделано)

| Ситуация | Статус цели | Суточный лимит | Пауза |
|---|---|---|---|
| Человек найден в чате после проверки | `invited` | +1 | обычный интервал аккаунта/кампании |
| RPC принят, после 5 проверок нет в чате | `failed` (unconfirmed) | не растёт | интервал после реального RPC сохраняется |
| `missing_invitees` | `failed` | не растёт | интервал освобождается |
| Privacy / not mutual | `privacy` | не растёт | без суточного cooldown |
| Техсбой до отправки Invite | снова `pending` | не растёт | без задержки |
| Обрыв после durable-маркера | остаётся `verifying` | не растёт | без повторного Invite, только проверка членства |
| FloodWait | `failed` | не растёт | cooldown по `seconds` |
| PEER_FLOOD | `failed` + restrict | не растёт | ручное восстановление |

Ключевые правила, которые зафиксированы:

1. **Успех = подтверждённое присутствие**, не «Telegram принял RPC».
2. **Privacy и недоступная цель** обрабатываются отдельно от успеха и от антиспам-ограничений.
3. **Технический сбой не запускает суточную паузу/квоту**.
4. **Лимиты Telegram не обходим**: после реально ушедшего Invite защитный интервал остаётся даже при тихой потере. Иначе софт начнёт долбить API чаще, чем позволяет антиспам.

Именно пункт про «суточную паузу после неподтверждённого инвайта» закрывается так: `successful_today` / дневная квота увеличиваются только в транзакции с `invite_confirmations.result='confirmed'`.

## 4. Что изменено в коде

### Очередь и Telethon-логика
- Двухфазный сценарий: claim → arm durable-маркер → Invite RPC → точечная проверка membership → finalize.
- `missing_invitees` не считается успехом.
- Presence проверяется серией опросов; unknown не превращается ни в успех, ни в ложный fail без повторной проверки.
- Privacy / PEER_FLOOD / FloodWait / tech — разные ветки обработчиков.

### SQLite
Раньше основной процесс плохо переживал конкуренцию с reporter’ом.

Сделано:

- `PRAGMA busy_timeout=30000` и connect `timeout=30` на основном соединении;
- атомарный claim цели в `BEGIN IMMEDIATE`;
- arm Invite RPC тоже в `BEGIN IMMEDIATE`;
- ошибка `database is locked` классифицируется как **технический** сбой, а не как ограничение Telegram.

### Файлы
- `app/db.py`
- `app/infrastructure/invitations/repository.py`
- `app/infrastructure/invitations/telegram.py`
- регрессионные тесты в `tests/`

## 7. Как принимать работу

Приёмка пакета B:

1. `successful_today` растёт только после подтверждённого присутствия.  
2. Unconfirmed / privacy / tech не увеличивают дневную квоту.  
3. Под параллельной нагрузкой нет стабильных `database is locked`.  
4. `pytest` зелёный.

Срок замечаний по этим пунктам — 5 рабочих дней с передачи сборки/PR.
