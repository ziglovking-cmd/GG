# TG Audience — парсер аудитории и мультиаккаунтный инвайтер

Локальное веб-приложение: собирает аудиторию чатов через MTProto и приглашает её
в целевой чат пулом аккаунтов с лимитами и обработкой всех отказов Telegram.

## Запуск

```bash
./run.sh
```

Откроется на http://127.0.0.1:8777. Сервер слушает только localhost.

### Запуск на VPS

Приложение содержит ключи Telegram-сессий, поэтому Docker-порт привязан только
к `127.0.0.1` сервера и не открыт всему интернету.

```bash
# На сервере, из каталога приложения
docker compose up -d --build

# На локальном компьютере — защищённый туннель
ssh -N -L 8777:127.0.0.1:8777 root@45.129.186.187
```

После открытия туннеля интерфейс доступен по адресу `http://127.0.0.1:8777`.
Данные сервера находятся в `data/` рядом с `docker-compose.yml`; файлы
`*.session` дают доступ к Telegram-аккаунтам и не должны передаваться третьим лицам.

## Первый запуск, по шагам

1. **Настройки → api_id / api_hash.** Получите на [my.telegram.org](https://my.telegram.org) →
   API development tools. Пара общая для всех аккаунтов, хранится в `data/config.json`.
2. **Аккаунты → добавить.** Телефон + прокси. Дальше «Запросить код» → ввести код →
   при включённой двухфакторке ввести пароль.
3. **Парсинг.** Выбрать аккаунт, загрузить список чатов, выбрать донора и источники.
4. **Инвайтинг.** Создать кампанию: целевой чат, аккаунты, доноры, фильтры → «Запустить».

## Авторизация аккаунтов и что хранится на диске

Вход в каждый аккаунт проходит прямо в карточке на вкладке «Аккаунты»:
«Запросить код» → код приходит **в приложение Telegram** на этот номер → ввести его →
если включена двухфакторка, ввести облачный пароль. Статус меняется на «в строю».

| Файл | Что внутри |
|---|---|
| `data/config.json` | api_id и api_hash |
| `data/app.db` | телефоны, настройки лимитов, спарсенная база, кампании |
| `data/sessions/acc_79xxx.session` | ключ авторизации Telegram |

Код подтверждения и пароль 2FA не сохраняются нигде: они уходят в Telegram один раз при
входе, в ответ приходит ключ авторизации — он и ложится в `.session`.

**Файл `.session` — это полный доступ к аккаунту.** Кто скопирует его себе, войдёт без
номера, кода и пароля. Папка `data/` уже в `.gitignore`; не кладите её в облако.
Скомпрометированный аккаунт лечится только через «Устройства» → завершить сеанс
в самом Telegram.

Сервер слушает только `127.0.0.1`. Наружу не уходит ничего, кроме запросов к Telegram
через ваши прокси.

## Что нужно сделать руками до инвайтинга

Три вещи, без которых кампания не пойдёт:

- **Все инвайтеры должны состоять в целевом чате** и иметь право добавлять участников.
  Приложение проверяет это при старте и молча выкидывает из ротации тех, у кого прав нет
  (запись появится в журнале).
- **Все инвайтеры должны состоять в чате-доноре и спарсить его каждый за себя.**
  Причина ниже.
- **Каждому аккаунту — свой прокси.** Десять аккаунтов с одного IP Telegram склеивает,
  и блокировка прилетает всему пулу сразу.

## Прокси

Задаётся в поле «Прокси» при добавлении аккаунта или кнопкой «Настроить» позже:

```
socks5://логин:пароль@1.2.3.4:1080
```

Без авторизации — `socks5://1.2.3.4:1080` или просто `1.2.3.4:1080`.
Поддерживаются также `http://` и `mtproxy://секрет@host:port`.

Кнопка **«Проверить прокси»** делает рукопожатие с Telegram через этот прокси и
показывает задержку и номер дата-центра. До 800 мс — хорошо, свыше 2,5 с — работать
будет, но инвайты начнут отваливаться по таймауту.

Какие прокси годятся:

| Тип | Как Telegram относится |
|---|---|
| Мобильные (4G/LTE) | лучший вариант: за IP оператора сидят тысячи живых людей |
| Резидентные | хорошо, IP домашнего провайдера |
| Серверные (датацентр) | плохо: диапазоны хостеров известны, аккаунт под подозрением сразу |
| Бесплатные MTProto | не использовать: чужой узел видит трафик |

Четыре правила важнее выбора провайдера:

1. **Один прокси — один аккаунт, навсегда.** Не перекидывайте прокси между аккаунтами:
   Telegram запоминает связку «аккаунт ↔ IP».
2. **Гео прокси = гео номера.** Номер +7 с немецкого IP выглядит как угон.
3. **Sticky-сессия, не ротация.** Telegram держит живое TCP-соединение; прокси, меняющий
   IP каждые пять минут, будет рвать сессию — это хуже, чем работа без прокси.
4. **Только IPv4.**

## Кто может получить список участников

| Тип чата | Кто видит список |
|---|---|
| Супергруппа | любой участник — если владелец не включил «Скрывать участников» |
| Канал-вещалка | только администратор; обычный подписчик получает `CHAT_ADMIN_REQUIRED` |
| Обычная группа до 200 человек | все участники |

Настройка «Скрывать участников» появляется в группах от 100 человек. Если донор — ваш,
просто проверьте, что она выключена, либо выдайте инвайтерам любое админ-право.
Если донор — канал, сделайте аккаунты админами (можно с пустыми правами) или собирайте
аудиторию по истории и реакциям.

Приходят объекты `User`, и в каждом — `access_hash`, выданный именно запросившему аккаунту.

## Про access_hash — главное ограничение мультиаккаунтности

Пользователь в Telegram адресуется парой `user_id + access_hash`, и хэш выдаётся
персонально аккаунту, который его получил. Спарсили аккаунтом A — аккаунт B по этим
данным получит `PEER_ID_INVALID`.

Обход:

- у кого есть **@username** — любой аккаунт резолвит его сам, хэш не нужен;
- у кого username нет — приглашает только тот аккаунт, который **сам видел** этого
  пользователя в общем чате.

Поэтому база хранит хэши в разрезе аккаунта (таблица `hashes`), а планировщик выдаёт
каждому воркеру только те цели, которые он реально способен пригласить. Цели, недоступные
никому, получают статус `no_hash`.

Практический вывод: заведите все 10 аккаунтов в чат-донор и спарсите его каждым.
Иначе доступна будет только часть базы — те, у кого есть @username.

Для этого есть кнопка **«Спарсить всеми аккаунтами»**: она прогоняет чат по очереди
каждым авторизованным аккаунтом с паузой 30 секунд между ними. Аккаунт, который не
состоит в чате, пропускается с записью в журнал.

## Источники аудитории

| Источник | Что даёт | Ограничения |
|---|---|---|
| Участники | полный список | супергруппы отдают ~10 000 обычной пагинацией; каналы — только админу |
| Глубокий обход | сверх 10 000 | перебор поисковых префиксов, дольше в десятки раз |
| История сообщений | тех, кто писал | самая конверсионная выборка, ловит и вышедших |
| Реакции | кто реагировал на посты | тёплая аудитория канала, медленно |

Если список участников закрыт правами, парсер автоматически переключается на историю.

## Лимиты и почему они такие

Дефолты специально консервативные:

| Параметр | Значение | Почему |
|---|---|---|
| Попыток в сутки | 25 | защитный потолок; пропуски из-за приватности приложение в него не включает |
| Пауза между инвайтами | 90–240 с, случайно | ровный интервал — маркер бота |
| Размер пачки | 8 | затем длинная пауза |
| Пауза между пачками | 45 мин | имитация живой активности |

Интервал свободно задаётся отдельно для каждого аккаунта. Например, `90–240` означает
случайную паузу в этом диапазоне, а `14400–14400` — ровно четыре часа. Все аккаунты
могут работать одновременно. Следующее разрешённое время хранится в SQLite, поэтому
остановка кампании или перезапуск контейнера не обнуляет уже начатое ожидание. Если
Telegram отказал из-за настроек приватности пользователя, цель сразу пропускается:
суточная квота не расходуется и интервал не запускается.

Свежие аккаунты начинайте с 5–10 в сутки и поднимайте за неделю. Аккаунт с новой SIM,
без аватара, истории и username улетает в спамблок на первых инвайтах.

## Обработка отказов

| Ошибка Telegram | Что делает приложение |
|---|---|
| `USER_PRIVACY_RESTRICTED` | помечает цель, идёт дальше. Это ~70% базы и не лечится |
| `USER_ALREADY_PARTICIPANT` | помечает «уже в чате» |
| `PEER_FLOOD` | выводит аккаунт из ротации на 24 часа, цель возвращает в очередь |
| `FLOOD_WAIT_X` | пауза ровно на X секунд, цель возвращается в очередь |
| `USER_BANNED_IN_CHANNEL` | аккаунт в спамблоке, пауза 48 часов, снят с кампании |
| `CHAT_ADMIN_REQUIRED` | у аккаунта нет прав в целевом чате, снят с кампании |
| `USERS_TOO_MUCH` | целевой чат заполнен, кампания остановлена |
| `PEER_ID_INVALID` | нет своего access_hash — цель помечена `no_hash` |

Начиная с layer 177 Telegram на неудачный инвайт не бросает ошибку, а возвращает
`missing_invitees`. Приложение это проверяет — иначе половина «успехов» была бы фиктивной.
Приватные отказы показываются отдельно, не входят в число приглашённых и не уменьшают
суточный лимит аккаунта. Зарезервированный интервал после такого отказа освобождается,
поэтому аккаунт сразу переходит к следующей цели.

## Уведомления Telegram

После подключения бота и личного чата приложение отправляет отдельное сообщение после
каждой фактической попытки приглашения, которая запускает интервал аккаунта. Сообщение
содержит кампанию, аккаунт, результат, время следующей попытки и свежие счётчики.
Расписание не привязано к часам `00:00`, `06:00`, `12:00` или `18:00`: каждая кампания
и каждый аккаунт уведомляют независимо в момент своей работы. Пропуски из-за настроек
приватности отдельного сообщения не создают. Свежую общую сводку можно запросить в боте
командой `/status` или кнопкой «🔄 Обновить отчёт».

## Реалистичные ожидания

10 прогретых аккаунтов × 25 инвайтов × ~25% успеха ≈ **60 вступлений в сутки**.
Остальное — приватность. Кампания на 5 000 целей идёт около двух недель.

Массовый инвайтинг нарушает условия использования Telegram. Аккаунты в пуле —
расходный материал: держите их отдельно от личного номера.

## Структура

```
app/config.py    — api_id/api_hash, пути, дефолты лимитов
app/db.py        — SQLite: аккаунты, чаты, участники, хэши, кампании, журнал
app/accounts.py  — пул Telethon-клиентов, авторизация, прокси, суточные квоты
app/parsing.py   — три источника аудитории, сохранение хэшей по аккаунтам
app/domain/      — правила инвайтинга, критерии выбора целей, доменные ошибки
app/application/invitations/ — сценарии и интерфейсы внешних зависимостей
app/infrastructure/invitations/ — SQLite, Telethon и доставка уведомлений
app/infrastructure/bot/ — Bot API, форматирование отчётов, обработка команд
app/bootstrap.py — сборка компонентов и внедрение зависимостей
app/inviting.py  — публичный фасад инвайтинга для остальных подсистем
app/api/         — HTTP-маршруты по ресурсам и схемы запросов
app/main.py      — сборка FastAPI, запуск/остановка задач и статика
web/             — интерфейс
data/            — база, сессии, config.json (в git не коммитить)
```

В инвайтинге зависимости направлены внутрь:
`api → application → domain`; инфраструктура реализует интерфейсы из
`application/invitations/ports.py`. В `domain` и `application` нет импортов
FastAPI, Telethon или SQLite. Это ограничение проверяет `tests/test_architecture.py`.

Сценарии разделены по ответственности: `targets.py` формирует очередь,
`scheduling.py` резервирует интервалы, `context.py` получает контекст,
`attempts.py` выполняет одну попытку, `verification.py` подтверждает членство,
`failures.py` обрабатывает отказы, `worker.py` управляет ротацией аккаунта,
`preparation.py` проверяет готовность, `recovery.py` восстанавливает воркер,
`campaigns.py` управляет кампанией. Состояние задач и блокировки принадлежат
экземпляру `CampaignRuntime`; новая сборка через
`create_invitation_application()` получает собственное состояние.

Перед Invite RPC репозиторий фиксирует durable marker. После неоднозначного
ответа или отмены выполняется только проверка членства, без повторной отправки.
Счётчики увеличиваются при атомарном подтверждении. Общий таймер аккаунта,
интервал кампании и защитные ограничения Telegram сохраняются.

`accounts.py`, `parsing.py`, `preflight.py`, `db.py` и отдельный процесс
`reporter.py` сохраняют прежние точки входа. Существующий пул аккаунтов подключён
через `AccountPort`, SQLite — через `InvitationRepository`; HTTP-контракт сохранён.

Проверка:

```bash
.venv/bin/python -m unittest discover -s tests -v
```
